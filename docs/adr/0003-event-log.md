# 0003. Event log

Status: accepted

## Context

The log is the only truth. An event is immutable, and a `redact` clears its content. The projection builds the records in two passes. The state machine and the supersede rule give one answer for any order of arrival.

## Decisions

| ID | Date | Decision | Context | Alternatives | Consequences |
| --- | --- | --- | --- | --- | --- |
| D-020 | 2026-11-04 | The log holds events, and a `redact` clears the content of its target. Each event has `id` (ULID), `at`, `op`, and `scope`, and a payload that belongs to the op. The ops are `note`, `amend`, `hide`, `redact`, `review`, `accept`, and `dismiss`. | The customer gave the data model. An immutable event keeps the history and gives a simple merge. | One mutable record for each note. One full snapshot for each write. | The first event of a note gives its identity. The state of a note is a projection over its events. A new op needs a new payload schema. |
| D-021 | 2026-11-04 | `pos` is not a field of an event. It is the ordinal of the creating event in the scope of the record, and it stays out of an export. | The addresses `#a-b` need an order, and two stores must merge without one global order. | A global counter in each event. An exported `pos`. A hash of the content. | The addresses are local to one store. A reader must not use a `pos` of another store. A merge keeps the order of the receiving log. |
| D-023 | 2026-11-04 | A `supersedes` stays inside one scope. The store refuses a cross-scope supersede with the error `CrossScopeSupersede`. | A note in `project:work` must not hide a note in `global:prefs`, where the agent has no write permission. | Allow each cross-scope supersede. Allow it for a user who owns both scopes. | A user who needs the effect writes a note in the other scope. The view of each scope stays predictable. |
| D-024 | 2026-11-04 | An event has two times. `at` is the time of the log, and `ts` is the time of the write of a note. | A note can enter the log after the time of the write. The log needs its own order. | One time for the both fields. | The log order comes from `at`. A note keeps the time of its write after an import. |
| D-025 | 2026-11-04 | The note event holds `review_at` only, the date of the next review. The record holds no `reviewed_at` field. | S-013 gave two fields, and S-017 keeps the date of the next review. | Keep `reviewed_at` as a second field. | The note event holds one date. |
| D-026 | 2026-11-04 | The prior-art table gives the principles, not the field names. The project takes the idempotency rule and names the key `idem`. The model holds no `sourceId`. | The customer gave the table as a source of ideas. A copied name disagrees with the event model. | Copy the field names of each implementation. Keep `sourceId` next to `idem`. | One name for one concept. D-018 keeps the rule, and this decision gives the name. |
| D-027 | 2026-11-04 | A `target` field names the `note` event. The store follows the chain of events of the note. | A later amend must find the same note, so the identity of a note must not move. | Let `target` name the newest event of the note. | An address stays valid after an amend. A reader needs the first event of a note only. |
| D-028 | 2026-11-04 | The projection is deterministic over the order `(at, id)`, and it makes two passes: one for the records and one for the operations. | A reference must find its target in each order of arrival, and two stores must agree without one clock. | One pass in the order of the log. A global clock for each event. | A target exists before the first operation. A `pos` and an arrival order change nothing. A reference to a later note still applies. |
| D-029 | 2026-11-04 | The supersede is irreversible. A target never leaves the state `hidden`, and `superseded_by` can name a hidden note. | Two notes can supersede one target, and each order of arrival must give one result. | Cancel the supersede when the other note hides. Give the field to the newest note. | The state stays monotone. The first note keeps the field. A reader does not need the state of the other note. |
| D-031 | 2026-11-04 | The state order is `live`, `hidden`, `proposed`, `deleted`. The ops `hide` and `dismiss` raise the state, and only an `accept` lowers it. | S-021 keeps a proposed record at `proposed` after a `hide`, and it gives the state `deleted` after a `dismiss`. Both answers give the order. | Put `hidden` above `proposed`. Put `deleted` below `proposed`. | A `hide` event changes no proposed record. A `dismiss` event reaches each record. The `accept` is the one transition that lowers the value. |
| D-032 | 2026-11-04 | An `accept` event clears the effect of an earlier `hide` event. The record becomes `live` and enters the view again. | S-022 returns a hidden proposed record to the view, and the state alone cannot keep a proposed record out of it. | Keep the record out of the view after an `accept`. Add a second flag to the record. | The order of the events decides the visibility. A `hide` after an `accept` takes the live record out of the view again. |
