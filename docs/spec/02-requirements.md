# Requirements

Type: `FR` is a function, `NFR` is a quality limit, `C` is an external constraint on the product.

Status: see [README.md](README.md#status-values).

This list holds cross-module requirements and pending behavior.
Code contracts own implemented rules within one module, without requirement identifiers.
The archived requirements, the refused items, and the originals of local rules are in
[02-superseded.md](02-superseded.md).
Use module invariants for module-wide rules. Use entity contracts for rules within one part of a module.

Some accepted rows below describe pending plugin behavior and the session import. The plugin implements configuration and registration.
Its context and tools, and the session import, are pending. See [06-architecture.md](06-architecture.md#remaining-work).

## Rules for new requirements

- Keep cross-module guarantees and pending behavior in this list.
- Put implemented local rules in module invariants or entity contracts. Keep requirement identifiers out of those contracts.
- Archive original local requirements with links to their owning code contracts.
- One requirement is one sentence. Do not put two different properties in one sentence.
- Write the behavior that the user can see. Do not write the mechanism, unless the customer
  gives the mechanism as a constraint.
- Write the test method before you set the status to `accepted`.
- Take each requirement from a customer statement. An example text in a statement is not a source.
