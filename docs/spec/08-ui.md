# UI

The standalone console supplies seven screens. The plugin tab remains pending.
The [console model contract](../../packages/core/src/domain/console.ts) owns the shared read models.
The [client contracts](../../packages/ui/src/client.ts) own the screens, the forms, the note inspector, and the theme choice.
The [message contract](../../packages/ui/src/i18n.ts) owns the text of each language.
The [host contract](../../packages/cli/src/ui.ts) owns HTTP, action validation, and the delete policy.

## Hosts

The command `memlens ui` hosts the console with its own styles.
The CLI builds the browser client as a separate bundle and serves it through a local HTTP server.
The flags `--port` and `--allow-delete` select the port and permit confirmed deletion.

The plugin must mount the tab `Memory` in `conversation.session.header` with the kind `memlens`.
The tab must use the same core models and the components of the harness UI.
The session selects one profile. The tab gives no profile selector.
See [REQ-417](02-requirements.md) and [REQ-028](02-requirements.md).

Both hosts must give the note actions: reviewed, amend, supersede, forget, and delete.
See [REQ-423](02-requirements.md).
Proposal approval must apply the ordinary operation and close the proposal in one logical transaction.
See [REQ-361](02-requirements.md).
The console must give compaction inputs and publish the answers through store validation.
See [REQ-459](02-requirements.md).

## Screens

- The overview shows one card for each visible scope and the assembled slice below the cards.
- The tree screen shows the slice lines of the selected scope. A range line opens its two children, and a note line opens the record.
- The catalog screen shows the direction lines of the visible scopes and the directions budget.
- The search screen finds notes in the selected scope or in every visible scope. The default filter takes every visible scope.
- The review screen lists the notes with a review date of today or earlier, with the five note actions.
- The proposals screen lists the pending proposals with accept and dismiss.
- The maintenance screen shows the build candidates, the line budgets, and the compaction job.

The tree screen shows the frontier of the model, so a range line and the notes inside that range never appear together.
See the [console contract](../../packages/core/src/domain/console.ts).
An amendment form changes the body, the document, the scope, the kind, and the supersedes of a note.
See the [projection contract](../../packages/core/src/domain/projection.ts) for the scope transfer, the kind change, and the supersedes of an amendment.
A compaction job without a merge input states that fact and opens no answer form.
See [REQ-518](02-requirements.md).

## Text and theme

The interface text supports the eight languages of the DSH set.
The language list gives each name in its own words, and a language without a text gives English.
See the [i18n contract](../../packages/ui/src/i18n.ts).
The theme choice is light, dark, or system, and the page follows the system setting while the choice is system.
The choice survives a reload.
See the [client contract](../../packages/ui/src/client.ts).

The standalone console holds no compaction and no harness session. It states no compaction state and no session snapshot state.
See the [client contract](../../packages/ui/src/client.ts).

## Data boundaries

The UI core holds no DOM, transport, or style. It reads the store through `StorePort`.
The standalone host supplies HTTP. The plugin must use the harness HTTP server.
The browser client imports core types only. Its bundle holds no backend implementation.

The [model contract](../../packages/core/src/domain/console.ts) owns empty scopes, the frontier lines, and stable read revisions.
The [form contract](../../packages/ui/src/client.ts) owns scope creation through its first note.
The standalone console reads current store data. It does not create a harness snapshot.

## Pending behavior

- The plugin must supply the session, materialization time, next trigger, and saved snapshot state.
- The compaction view must supply local attempts, active builds, backoff, and failures when a compaction runs in that host.
- The catalog map must show budget use for each node group and the rule that reduces old nodes. That rule remains undefined.

The compaction view must derive candidates from dirty ranges and local runtime state.
It must read no stored work list. A restart resets local attempts and backoff.
See [S-142](../statements.md#s-142).
